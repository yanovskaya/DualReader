# Глава 02. Архитектура и структура папок

> **Зачем эта глава:** понять, где какой код лежит и почему именно так.

## Трёхслойная архитектура

В проекте используется классический подход: код разделён на три слоя, каждый со своей ролью.

```
┌─────────────────────────────────────────────────┐
│  CONTROLLER  ← принимает HTTP-запросы           │
│       ↓        отдаёт JSON-ответы               │
│  SERVICE     ← бизнес-логика, «что делаем»     │
│       ↓                                          │
│  REPOSITORY  ← работа с базой данных            │
│       ↓                                          │
│  DATABASE    ← PostgreSQL                       │
└─────────────────────────────────────────────────┘
```

**Правила:**
- **Controller** не лезет в БД и не знает SQL. Он только принимает запрос, валидирует параметры, зовёт сервис, оборачивает ответ.
- **Service** не знает про HTTP (никаких `request`, `response`). Он содержит логику и зовёт репозитории.
- **Repository** работает только с одной таблицей.

**Зачем так?**
1. Каждый слой можно менять независимо. Поменяли HTTP на gRPC — только контроллеры переписали.
2. Каждый слой легко тестировать отдельно (мокаешь нижний слой — проверяешь верхний).
3. Любой человек, увидевший структуру, сразу понимает, где что искать.

## Структура папок Java-проекта

В Java принято раскладывать классы по **пакетам** (packages). Пакет = папка. Имя пакета = «обратное доменное имя» проекта, например `com.lingua.api`.

Папки на диске **обязаны** один в один повторять имя пакета. То есть `com.lingua.api` живёт в `com/lingua/api/`. Это требование самого языка.

Полная структура нашего бэкенда:

```
artifacts/api-server/
├── pom.xml                                ← Maven-конфиг (зависимости, сборка)
├── src/
│   ├── main/
│   │   ├── resources/
│   │   │   └── application.properties     ← настройки приложения
│   │   └── java/
│   │       └── com/lingua/api/
│   │           ├── LinguaApiApplication.java   ← главный класс (метод main)
│   │           ├── config/                ← бины конфигурации (DataSource, CORS, Async)
│   │           │   ├── DatabaseConfig.java
│   │           │   ├── AsyncConfig.java
│   │           │   └── CorsConfig.java
│   │           ├── model/                 ← Entity-классы (= таблицы БД)
│   │           │   ├── Book.java
│   │           │   └── Paragraph.java
│   │           ├── repository/            ← интерфейсы для работы с БД
│   │           │   ├── BookRepository.java
│   │           │   └── ParagraphRepository.java
│   │           ├── service/               ← бизнес-логика
│   │           │   ├── BookService.java
│   │           │   ├── TranslationService.java
│   │           │   ├── DictionaryService.java
│   │           │   ├── OpenAiService.java
│   │           │   └── EpubParser.java
│   │           └── controller/            ← HTTP-эндпоинты
│   │               ├── HealthController.java
│   │               ├── BookController.java
│   │               ├── DictionaryController.java
│   │               └── UploadController.java
│   └── test/                              ← тесты (пока пусто)
└── target/                                ← сюда Maven кладёт скомпилированные .class и .jar
```

## Что где лежит — по слоям

| Слой | Папка | Что внутри |
|---|---|---|
| HTTP | `controller/` | классы с `@RestController`, обрабатывают запросы |
| Логика | `service/` | классы с `@Service`, основная работа |
| БД | `repository/` | интерфейсы, наследующие `JpaRepository` |
| Модели | `model/` | классы с `@Entity`, по одному на таблицу |
| Настройки | `config/` | классы с `@Configuration` для тонкой настройки |

## Стандартные имена

В Java/Spring сложились конвенции имён, которым все следуют:

- Сущность — единственное число: `Book`, `Paragraph` (НЕ `Books`).
- Репозиторий — `<Сущность>Repository`: `BookRepository`.
- Сервис — `<Имя>Service`: `BookService`, `TranslationService`.
- Контроллер — `<Имя>Controller`: `BookController`, `HealthController`.

Если придерживаешься этих конвенций — твой код понятен любому Java-разработчику с первого взгляда.

## Главное правило: одна папка — одна ответственность

Не клади контроллер в папку `service/`. Не клади Entity в `controller/`. Кажется мелочью — но если нарушить, через месяц код становится месивом.

Открой `artifacts/api-server/src/main/java/com/lingua/api/`. Найди:
- Где лежит `BookController.java`.
- Где лежит `BookService.java`.
- Где лежит `BookRepository.java`.

Открой `BookController.java` и поищи в нём слово `paragraphRepo`. Найдёшь? Это нарушение правила! Контроллер должен звать сервис, а не репозиторий напрямую. (Это сделано из лени для одного эндпоинта. В идеале — починить.)
